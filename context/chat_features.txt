1. **Media, Links and Docs** on direct-chat, group-details and broadcast-list-details pages.
2. **Starred** on direct-chat, group-details and broadcast-list-details pages.

4. **Groups in common**, exclusively on an individual contact's details page.

## 4. Media, Links and Docs

### User experience

Build a reusable shared-content screen that accepts a properly typed conversation context:
- Direct chat.
- Group chat.
- Broadcast list.

Use a clear three-tab interface:
- Media
- Links
- Docs

Follow the existing design system. Support safe areas, small screens, loading states, errors, empty states, pagination and refresh.

#### Media tab

Display supported image, video, audio and other media attachments according to the existing product capabilities.

For images and videos:
- Use a responsive grid with appropriate thumbnails.
- Show a loading placeholder and a useful fallback when a thumbnail is unavailable.
- Open the existing image viewer or video player.
- Navigate to the original message when that is supported by the current chat architecture.

For audio and voice messages:
- Reuse the existing audio playback implementation if present.
- Show duration and date where available.
- Do not introduce a second, incompatible media-player architecture.

Use the real attachment metadata. Do not fabricate thumbnails, media sizes, timestamps or preview content.

#### Links tab

Extract links from persisted messages using a reliable URL-detection utility, or reuse an existing parser.

Requirements:
- Support multiple URLs in one message.
- Avoid duplicate entries for the same message and URL.
- Preserve the original message ID, conversation context, sender and timestamp.
- Display a safe URL/hostname and optional preview metadata.
- Generate or fetch previews only if a suitable, secure existing mechanism is available.
- Do not make arbitrary server-side requests to user-supplied URLs without SSRF protections.
- Do not fetch previews in a way that leaks private message contents or credentials.
- Handle malformed URLs and unsupported schemes safely.
- Opening a link must use safe URL validation and the existing external-link handling.

If a message has a URL but no preview metadata, show a useful link row rather than hiding it.

#### Docs tab

Display document attachments with:
- Filename.
- File extension or MIME type.
- File size, when known.
- Sender and date.
- Optional document icon or thumbnail where supported.

Tapping a document must use the existing secure attachment-download flow. Generate short-lived authorized URLs through the backend if required by the existing S3 architecture. Never expose private S3 credentials or create public object URLs.

Handle missing files, expired download URLs, failed downloads, unsupported file types and retry.

### Data and performance

Use the actual `message_attachments` relationship and persisted messages. Inspect how URLs, attachment metadata, MIME types, storage keys and broadcast delivery records are currently represented.

Requirements:
- Filter content by the correct conversation/list context.
- Respect the logged-in user's access to the conversation.
- Support cursor-based pagination or the project's established pagination approach.
- Sort newest-first by a deterministic order.
- Use appropriate database indexes for frequent queries.

If the existing schema cannot efficiently support these queries, introduce a migration or appropriate query/index improvement. Do not create a redundant media table without demonstrating why it is necessary.

### Navigation

When an item is tapped, open the original message or media viewer in the correct conversation where possible.

If the message is no longer available or the user no longer has access, display a safe fallback and do not bypass authorization.

## 6. Clear Chat — only for the authenticated user

This feature is critical: clearing a chat must never globally delete the shared conversation or remove history from other participants.

### UI and confirmation

Add a clearly visible Clear Chat action to each applicable details page.

Before execution, display a confirmation screen/modal that explains:
- Only this user's chat history will be cleared.
- Other participants' messages and histories will remain unchanged.
- The user will remain in the conversation/group.
- The chat/list entry will remain available.
- This action may not be recoverable unless the application has an explicit recovery mechanism.

Provide a choice to retain or clear starred messages.

If the current application has a local media cache, distinguish clearing chat history from deleting the user's downloaded media. Do not delete unrelated files or other conversations' cached attachments.

Prevent accidental taps, duplicate submissions and concurrent clear operations. Show a loading state, success feedback and a recoverable error state.

### Required semantics

For a direct chat:
- Hide the cleared history from the current user.
- Do not delete messages from the other participant's history.
- Keep the direct conversation itself.
- Keep subsequent new messages visible.
- Keep delivery/read receipts and normal message processing intact.

For a group:
- Hide the cleared history from the current user.
- Do not affect the history of any other member.
- Do not remove the user from the group.
- Do not modify membership, group settings or group messages globally.

For a broadcast list:
- Clear only the current owner's local/list-specific history view as appropriate.
- Do not delete shared messages or recipient-specific direct messages.
- Do not modify recipients, list membership or the list itself.

### Backend persistence and multi-device behavior

Do not implement Clear Chat by merely deleting local SQLite rows. A client-only deletion would allow old messages to reappear on the next synchronization.

Inspect the current message synchronization and pagination design. Implement a server-persisted per-user clear state that synchronizes across that user's devices.

Possible designs include:
- A per-user/per-conversation clear-through marker with a deterministic ordering key.
- A per-user/per-conversation clear state combined with an explicit per-user starred-message preservation mechanism.
- A per-user/per-message visibility/tombstone model if the current architecture requires it.

Choose the simplest correct design for the actual schema.

If using a clear-through marker:
- Use a deterministic message ordering key, not timestamps alone if timestamp collisions or late-arriving messages can cause ambiguity.
- Ensure messages created after the clear operation remain visible.
- Ensure messages already persisted before the clear do not reappear during pagination, reconnect, offline sync or another-device login.
- Define the behavior of delayed/offline message synchronization.
- Apply the clear filter to all relevant history endpoints, search results, local caches and shared-content views.

If using per-message tombstones:
- Make the operation transactional and idempotent.
- Do not change global message-deletion state.
- Avoid creating unbounded work in a synchronous request for large conversations; use a durable background job if required.
- Ensure all user-visible endpoints respect the tombstones.

The backend must derive the user identity from the authenticated session. Never accept a client-supplied user ID as authority to clear someone else's history.

### Starred-message handling

Before implementation, inspect the existing starred-message semantics and decide how retained stars work with the clear marker.

If the user chooses to preserve stars:
- Preserve the selected user's starred entries.
- Ensure the Starred section remains usable.
- Avoid exposing cleared messages through ordinary history, search or shared-content tabs.
- If opening a retained star requires special behavior, implement it explicitly and consistently.

If the user chooses to clear stars too:
- Remove only the current user's starred entries for the selected context.
- Never unstar the same message for another participant.

### Cache and synchronization

After a successful clear:
- Invalidate or update relevant React Query caches.
- Clear or update the relevant Zustand state.
- Delete or mark the appropriate user's SQLite cached records.
- Ensure pending sync operations do not reinsert cleared messages.
- Broadcast a user-scoped clear-state update to that user's other active sessions/devices where the existing architecture supports it.
- Do not send a global message-deletion event to other participants.

The UI should reflect the cleared state immediately after successful server confirmation, while handling failures without pretending the operation succeeded.

## 7. Groups in common — direct chats only

Implement a Groups in common section on the individual contact's details page only.

WhatsApp's purpose for this feature is to help a user identify groups shared with a contact.

### Backend query and authorization

Create an authenticated endpoint or extend the existing contact-details endpoint to return the groups in which both:
1. The authenticated user is currently a member.
2. The selected contact is currently a member.

Requirements:
- Verify the selected contact and relevant direct-chat access according to existing policies.
- Return only groups that the authenticated user is currently authorized to view.
- Do not return groups the authenticated user has left or been removed from.
- Do not return groups the other contact has left or been removed from.
- Do not expose hidden/internal group metadata.
- Return only fields required by the UI, such as group ID, name, photo URL or existing avatar representation, and permitted preview metadata.
- Use indexed membership joins and avoid one query per group.
- Handle duplicate memberships and stale membership records safely.
- Use the project's existing group visibility rules.

The query should derive the intersection of the two users' current group memberships, not infer common membership from chat history or phone contacts.

### Frontend

On individual contact details:
- Add a Groups in common section.
- Show a count if useful.
- Display group avatar, group name and any permitted subtitle.
- Provide an empty state such as "No groups in common".
- Support loading, error and refresh states.
- Navigate to a group only after normal authorization and membership checks.

Do not display the contact's other groups unless the logged-in user is also a member.

Do not show this section on group details, broadcast-list details or unrelated profile pages.
