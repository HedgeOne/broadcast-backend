# Implement the Complete WhatsApp-Style Groups Module in Broadcast

## Objective

Implement the complete **Groups module** in Broadcast, a WhatsApp-inspired messaging application built with Expo React Native and a Node.js backend.

This is an implementation task. Inspect the repositories, design the implementation, modify the actual code, create database migrations, implement APIs and real-time behavior, build the UI, add tests, and verify the result.

Do not stop at a plan, mockup, scaffold, or list of recommendations. Implement the entire feature across the frontend and backend.

The current application is in the demo stage. Existing messages are demo data, so you may refactor the existing messaging architecture where necessary. However, preserve working authentication, user profiles, contact discovery, direct chats, navigation, and established design patterns.

Inspect the actual code before changing it. Do not assume that an existing table, route, or feature is fully implemented just because its name exists.

## 3. Group creation

Implement a complete group creation flow.

### Create group screen

Users must be able to:

1. Select multiple registered Broadcast users from their contacts or the existing user search.
2. Search by name or phone number.
3. Select and deselect participants.
4. See selected participants as removable chips or avatars.
5. Enter a group name.
6. Optionally set a group photo.
7. Optionally enter a group description.
8. Review the selected participants before creation.
9. Create the group and navigate directly to its conversation.

Validate group names, descriptions, participant selection, authorization and any group-size limit supported by the chosen product policy.

Do not invent registered users or populate the interface with fake contacts.

If the current contacts implementation returns unmatched phone numbers, do not automatically create accounts or treat unmatched contacts as group members. Only registered, eligible Broadcast users can join.

### Creator permissions

The group creator becomes the initial group owner and administrator.

The creator must be included in the membership records, and the group creation transaction must not leave behind a partially created group if inserting members or chat records fails.

Create the group, initial membership, group chat association and initial system event atomically.

Prevent duplicate membership records and duplicate group creation caused by repeated client requests.

Allow authorized administrators to edit group name, description and photo.

If only administrators are allowed to edit group information, enforce that rule on the server rather than relying on disabled frontend buttons.

Support an appropriate empty state for a group without messages or a photo.

## 5. Group roles and permissions

Implement explicit, server-enforced group roles.

Use a clearly defined role model:

- **Owner:** The group's original owner or current designated owner, with the highest level of authority.
- **Admin:** A member with administrative permissions.
- **Member:** A regular participant.

Define the role hierarchy centrally and use it consistently throughout the backend and frontend.

### Owner capabilities

- All normal administrator capabilities.
- Transfer ownership to another eligible group member.
- Promote members to administrator and demote administrators where allowed by the role policy.
- Remove administrators and members where allowed by the role policy.
- Manage group-wide settings.
- Delete the group according to the documented deletion policy.

Ownership transfer must be atomic and auditable. Prevent a group from entering an invalid state with no owner.

### Administrator capabilities

- Add members where group settings permit.
- Remove members where permitted.
- Promote eligible members and demote administrators according to the role hierarchy.
- Edit group information.
- Manage group permissions.
- Approve or reject join requests if approval-based joining is enabled.
- Manage invite links.
- Moderate group messages according to the implemented message-moderation policy.

Do not allow an administrator to perform an operation forbidden by the role hierarchy.

### Member capabilities

- View group information and eligible member profiles.
- Send and receive group messages when posting is permitted.
- Reply to messages.
- React to messages.
- Mention other group members.
- Mute or unmute group notifications.
- Leave the group.
- Report inappropriate content or users using the existing privacy/reporting infrastructure.

Members must not be able to perform administrator-only operations by directly calling backend endpoints.

### Permission enforcement

Implement a centralized group authorization service.

Every sensitive operation must verify:

- The authenticated user.
- Group existence and status.
- Current membership.
- Current role.
- Group-specific permission settings.
- Target member eligibility.
- Whether the action is allowed for that role and target.

Never trust a client-supplied role, owner ID, sender ID or membership flag.

Add tests for unauthorized API requests, role escalation, self-promotion, unauthorized removal, invalid ownership transfers and actions against nonmembers.

## 6. Group settings and participation controls

Implement a group settings model that includes:

- Who can edit group information: all members or administrators only.
- Who can send messages: all members or administrators only.
- Who can add participants: all members or administrators only.
- Who can approve new members, where approval is enabled.
- Whether invite links are enabled.
- Whether new members may see earlier messages, subject to the product's history-sharing policy.

Persist settings in PostgreSQL and enforce them on the backend.

Changing a setting must take effect immediately for subsequent authorized operations.

The frontend should accurately display the current policy and indicate why an action is unavailable.

Do not implement controls that look functional but have no backend effect.

## 7. Add, remove and invite members

### Add participants

Allow authorized users to add existing Broadcast users through contact selection or user search.

Handle:

- Existing members.
- Duplicate selections.
- Blocked users.
- Users who have left the group.
- Inactive or unavailable accounts.
- Groups at their configured member limit.
- Concurrent membership changes.
- Unauthorized additions.

Apply the same validation to every API request, regardless of the UI path used.

### Remove members

Authorized administrators can remove eligible members.

When a user is removed:

- Revoke their access to future group messages.
- Prevent new subscriptions and delivery to their device through this group.
- Reject their future message submissions.
- Preserve historical messages according to the application's history-retention policy.
- Update member count and chat-list metadata.
- Emit a group system event.
- Notify affected clients through the supported real-time mechanism.

Do not automatically expose old history to newly added members without an explicit, documented policy.

### Leave group

Implement a Leave Group action with confirmation.

Handle ownership transfer or the last remaining owner/admin/member correctly.

Leaving must revoke future access and subscriptions. It must not accidentally delete the entire group unless the documented policy explicitly requires it.

### Invite links

Implement secure group invite links if compatible with the current deep-linking architecture.

Requirements:

- Cryptographically unpredictable invite tokens.
- Store only a secure token hash where practical.
- Support token revocation and regeneration.
- Support expiry and optional use limits.
- Enforce group status, capacity and join policy.
- Support approval-required joining if enabled.
- Prevent unauthorized users from bypassing group restrictions.
- Do not reveal private group membership information merely by opening a link.

Integrate with the existing Expo Router deep-link handling. If a full invite-link flow depends on external link infrastructure that is not configured, implement the secure backend contract and in-app flow, then document the remaining setup rather than pretending external links work.

## 12. Real-time group delivery

Extend the current WebSocket architecture or the existing messaging transport. Do not create a separate incompatible transport for group messages.

Requirements:

- Authenticate each connection.
- Verify group membership before subscribing a user to a group stream.
- Route events only to eligible group members.
- Stop delivery after a member leaves or is removed.
- Handle reconnects and missed events.
- Prevent duplicate visible messages.
- Handle concurrent sends.
- Enforce rate limits.
- Validate all payloads.
- Avoid broadcasting administrative data to unauthorized members.

Persist accepted messages before acknowledging durable acceptance.

Use a transactional outbox or an equivalent durable event-dispatch mechanism if required by the current architecture, so a backend restart cannot silently lose an accepted message or membership event.

Use PostgreSQL as the durable source of truth and Redis only for ephemeral coordination, routing or caching where appropriate.

Do not assume that WebSocket delivery is durable.

## 13. Group message persistence and data model

Inspect the existing schema first and reuse `groups`, `group_members`, `chats`, `chat_members`, `messages`, `message_reactions` and other existing entities where appropriate.

Define the relationship between a group and its conversation explicitly.

Do not create a second message table exclusively for group messages unless there is a compelling architectural reason.

Implement or adapt the following concepts as needed:

- Group metadata.
- Membership and role.
- Membership status and lifecycle timestamps.
- Group settings.
- Group-to-chat mapping.
- Message sender and conversation association.
- Reply references.
- Mention metadata.
- Reactions.
- Membership and administrative system events.
- Invite tokens and join requests.
- Per-user group mute and read state.
- Durable event dispatch.

Use foreign keys, unique constraints, indexes, appropriate delete behavior and transactions.

Prevent duplicate membership, invalid ownership and cross-group message access.

Design migrations to be reproducible.

Do not silently destroy production data. Demo-only tables may be reset only through an explicit, documented development migration or reset procedure.

Keep private application secrets out of database migrations and seed data.

## 14. End-to-end encryption boundary

The OpenE2EE integration has not yet been established as a completed, production-ready feature.

For this task:

- Do not invent encryption or claim group E2EE is implemented.
- Do not store private cryptographic keys in PostgreSQL or Redis.
- Keep group authorization and membership logic independent of the cryptographic transport.
- Isolate message transport behind a service boundary so group messaging can be integrated with an E2EE protocol later.
- If the existing direct-chat transport currently uses Base64-encoded plaintext, do not describe it as encrypted.
- Do not introduce a second delivery path or silently route messages through an unconfigured OpenE2EE relay.

Group messaging should function in the current Expo Go development environment without requiring native E2EE modules.

Document the exact security boundary and remaining E2EE work.
