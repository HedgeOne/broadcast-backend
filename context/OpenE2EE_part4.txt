## Priority 2 — Make media encryption enforceable end to end

Inspect the existing streaming AEAD implementation, media upload/download routes, presigned S3 URLs, `message_attachments`, migration `014_e2ee_media.sql`, and all callers for direct messages and broadcast lists.

Implement and test:

1. Attachment bytes are encrypted on the sending device before any upload begins.
2. S3 receives ciphertext only.
3. Media keys and decryption parameters exist only inside the appropriate encrypted message envelope and authorized device state.
4. The backend cannot accept a client-declared `content_encrypted: true` flag as proof that uploaded bytes are ciphertext.
5. Validate the encrypted-upload contract using authenticated, server-enforced upload metadata and the actual supported client protocol. Do not attempt to infer cryptographic validity from MIME type or filename.
6. Legacy unencrypted attachment paths cannot be used to bypass E2EE for new messages.
7. Presigned URLs remain private, short-lived, and appropriately authorized.
8. Filenames, thumbnails, captions, generated previews, and other derived media do not leak plaintext through server processing, object metadata, logs, or push payloads.
9. Tampered, corrupted, truncated, or incorrectly keyed media fails integrity validation and is not presented as a valid decrypted file.
10. Interrupted transfers, expired URLs, retries, and large-file handling work without persisting plaintext into an unsafe queue or temporary file.

Apply migration `014_e2ee_media.sql` only to the intended local development/test database when the environment has been positively identified as non-production. Inspect the migration and migration runner first. Never reset a database to apply it.

Add regression tests for all applicable upload and download routes, including attempts to bypass the encrypted-upload requirement.

## Priority 3 — Prove group membership rotation and forward access restrictions

Inspect every group lifecycle path, including group creation, member addition, invitation acceptance, approval, member removal, leaving, role changes, and group deletion.

The latest implementation reportedly calls `handleGroupMembershipChange`. Verify that this call uses the SDK correctly and that required protocol state is distributed and persisted.

Implement or fix:

1. Rotation and state distribution for every membership transition required by the SDK.
2. Correct ordering between membership authorization changes, key rotation, state persistence, and subsequent message delivery.
3. Retry-safe handling of partial failure and concurrent membership changes.
4. Prevention of removed members receiving or decrypting messages sent after their removal.
5. Prevention of new members accessing earlier messages unless an explicitly supported and authorized history-sharing feature exists.
6. Correct operation when an authorized member is offline or has multiple devices.
7. Correct failure behavior when rotation, distribution, or persistence fails.
8. Prevention of further sends using stale group cryptographic state when rotation is required but incomplete.

Do not assume a successful return from a membership-change handler proves the group was securely rotated. Use supported SDK state and operations to verify the resulting behavior.

### Required group tests

Use separate identities and native simulator devices where necessary:

- Create a group and exchange encrypted messages among authorized members.
- Add a member and verify the intended access boundary.
- Remove a member and send a new message.
- Verify the remaining authorized members can decrypt the new message.
- Verify the removed member cannot decrypt the new message and cannot receive its valid envelope.
- Verify historical-message behavior matches the documented protocol guarantees.
- Repeat with an offline member, multiple recipient devices, retries, and a failed rotation/distribution attempt.
- Confirm no group message body or key material is exposed to PostgreSQL, Redis, WebSocket payloads, or logs.

Do not claim forward secrecy or post-removal confidentiality beyond what the SDK's documented guarantees and tests establish.

## Priority 4 — Complete authenticated reaction and deletion operations

Inspect the current reaction and deletion implementations, REST endpoints, database schema, authorization checks, WebSocket events, and local message state.

Implement protocol-authenticated operations that preserve the product's existing semantics.

Requirements:

1. Authenticate the actor and validate that the actor is authorized to perform the operation on the specific message and conversation.
2. Bind each operation to the correct conversation, message identifier, actor, operation type, and relevant state/version using supported protocol mechanisms.
3. Prevent clients from forging reactions, deletions, or operation events for another user.
4. Prevent unauthorized edits or deletions from being accepted by changing a REST request body or WebSocket payload.
5. Keep operation payloads encrypted where they contain protected content or message-specific sensitive information.
6. If an operation is represented by minimal server-visible metadata, explicitly document the metadata and cryptographic authorization model. Do not claim that a REST-only event is E2EE-authenticated unless it is actually authenticated by the protocol.
7. Preserve the distinction between deleting a message for oneself, deleting it for everyone if supported, and clearing local chat history.
8. Make retries and duplicate events idempotent.
9. Synchronize the resulting state correctly across authorized devices.
10. Fail closed on missing keys, invalid authentication, stale state, unsupported operations, or decryption/authentication errors.

Do not create an edit-message feature if no edit API exists. Do not delete the other participant's local history when a user clears their own chat.

Add negative tests for forged actor IDs, unauthorized message IDs, cross-conversation operations, duplicate operations, stale events, invalid authentication, and unauthorized deletion.

## Priority 5 — Audit and fix local cache confidentiality

Inspect every table, column, index, query, migration, and persistence path in `broadcast.db`, not just `messages.text` and `messages.extra`.

Find all plaintext-bearing or content-derived data, including:
- Message text and quoted bodies.
- Captions and filenames.
- Link previews and extracted URLs.
- Shared-media/document metadata.
- Starred-message data.
- Search-related state.
- Pending/outgoing message queues.
- Decrypted temporary files and derived previews.
- Any denormalized chat or broadcast preview.
- Other cached content or protocol pointers that the UI might mistake for plaintext.

Implement an appropriate, maintainable at-rest encryption design.

Requirements:

1. Use authenticated encryption and a properly protected key stored through the existing secure-storage design or an appropriately reviewed SQLCipher design.
2. Keep the SDK-owned protocol database separate from the application database.
3. Correctly scope data and keys to the authenticated account/device.
4. Prevent account switching from exposing another account's cached plaintext or encryption keys.
5. Ensure logout clears sensitive in-memory state.
6. Ensure search decrypts only locally and does not leak plaintext to the server.
7. Check SQLite journal/WAL files, temporary files, exports, backups, and migration artifacts for plaintext persistence.
8. Migrate existing local records safely without deleting data indiscriminately.
9. Handle key loss, corruption, and migration failure explicitly.
10. Ensure encrypted local content is not accidentally decrypted by generic DTO mappers or preview components.

Do not assume that sealing two columns encrypts the entire SQLite database. Choose the narrowest secure implementation consistent with the current architecture and preserve existing behavior.

Add tests for local persistence, restart, account switching, logout, search, starred messages, shared content, and migration failure. Include a test that proves a recognizable synthetic sentinel message is absent from the relevant unencrypted database content and indexes.
