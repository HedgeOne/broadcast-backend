# Implement Complete S3 Media Storage and WhatsApp-Style Media Sharing in Broadcast

## Objective

Implement a complete, secure, S3-backed media-sharing system throughout Broadcast.

This includes AWS S3 integration, authenticated upload authorization, direct uploads, attachment metadata, secure downloads, local caching, media previews, the message composer, real-time delivery, and integration with direct chats, group chats and broadcast lists.

This is an implementation task. Inspect the actual repositories, modify the code, add migrations and tests, run available checks, fix failures, and provide a final implementation report. Do not stop at a plan, scaffold or UI mockup.

## 5. Implement secure upload sessions

Implement authenticated upload-session creation and finalization APIs using the existing Fastify conventions.

A typical lifecycle should be:

1. The authenticated client requests an upload session with filename, intended media category, size and MIME type.
2. The backend validates the request and applicable upload policy.
3. The backend creates an upload-session record or equivalent durable state.
4. The backend generates a unique object key and short-lived presigned upload URL.
5. The client uploads the bytes directly to S3.
6. The client calls the finalization endpoint.
7. The backend verifies that the object exists and validates its actual metadata against the upload session.
8. The backend marks the upload as ready for message attachment.
9. The client sends a chat message referencing the authorized attachment ID.

The backend must not accept an arbitrary client-supplied storage key as proof of upload ownership.

A failed or abandoned upload must not create a visible message attachment.

Prevent the same upload session from being finalized multiple times into duplicate attachment records.

Presigned URL expiration must be short enough to reduce abuse but long enough for normal mobile uploads. Use an appropriate configurable default.

### File validation

Perform validation on both the client and backend.

At minimum, validate:

- File size.
- Allowed file category.
- MIME type.
- File extension where relevant.
- Filename length.
- Upload ownership.
- Upload-session status.
- S3 object existence.
- Actual object size.
- Expected content type.
- Authorization to attach the file to a message.

Do not trust client-supplied MIME type or filename alone.

Block executable and dangerous content types by default. Allow ordinary images, videos, audio and documents, including PDF, DOCX, XLSX, PPTX, CSV, TXT and other explicitly permitted document formats.

For generic files, use a controlled allowlist and safe download/open behavior. Do not execute uploaded content.

Where practical, validate file signatures or inspect content types beyond the supplied HTTP headers.

### Size limits

Start with a configurable default maximum of **50 MB per file**.

Keep the maximum centralized in backend configuration and enforce it on the server.

Do not silently increase limits simply because S3 permits larger objects.

Implement the upload abstraction so that multipart upload can be added for larger files later. If multipart upload is implemented now, enforce limits for the entire upload, authorize every required operation and clean up incomplete uploads.

Do not buffer entire large files in Node.js memory.

## 6. Secure download and access control

The S3 bucket remains private.

Implement a backend endpoint that authorizes access to an attachment before issuing a presigned download URL.

The backend must verify:

- The attachment exists.
- The associated message exists.
- The authenticated user has permission to access that message.
- The user is an authorized participant in the relevant direct chat or group.
- For broadcast deliveries, access is authorized through the recipient's corresponding direct message.
- The attachment has not been deleted, expired or otherwise made unavailable.

Never assume that knowing an attachment UUID grants access.

Do not expose another user's broadcast-list membership or list name when retrieving a broadcast attachment.

Do not return permanent public S3 URLs.

The download URL should be short-lived, and the client should refresh it when expired.

Ensure that removed group members cannot use newly issued download URLs to access future restricted content.

Document the unavoidable limitation that an already-issued presigned URL remains usable until expiry unless the object or its access conditions change.

## 10. Upload progress, retries and local caching

Use Expo-compatible file APIs to transfer files without reading large files entirely into JavaScript memory.

Implement:

- Upload progress.
- Download progress where supported.
- Cancel upload.
- Retry failed upload.
- Retry failed download.
- Network interruption handling.
- Expired presigned URL recovery.
- App restart recovery for pending upload metadata.
- Cleanup of abandoned local temporary files.
- Local attachment cache indexing.

Use SQLite for local metadata and download state, not as the remote media store.

Keep downloaded media in an appropriate app-controlled filesystem location.

Use deterministic local cache identifiers derived from stable attachment IDs. Do not treat cached files as authoritative server state.

Avoid unbounded cache growth. Implement reasonable cache cleanup and avoid deleting files that are actively being displayed or uploaded.

Ensure that cached attachments are associated with the correct account and do not leak between accounts after logout or account switching.

## 11. Group chat integration

Reuse the same attachment pipeline for group messages.

- An authorized group member uploads media through the shared service.
- The attachment is linked to the group's normal message record.
- Eligible current group members receive the message metadata through the existing delivery mechanism.
- Recipients download the attachment through the authorized endpoint.
- Removed members cannot access new group content.
- Message ordering, sender information, delivery receipts and read receipts remain consistent.
- Group media must not be delivered to unrelated users.
- Do not create a separate group attachment system.

Reuse existing group role and membership authorization services.

Do not trust a client-supplied group ID without checking current membership and posting permissions.

## 12. Broadcast list integration

Reuse the same media service for broadcast lists.

A single broadcast send operation should produce the appropriate recipient-specific direct messages using the existing broadcast delivery architecture.

Each recipient sees the attachment in their ordinary one-to-one chat with the sender.

Recipients must not see the broadcast list's name or the other recipients.

Use the same S3 object for a shared attachment when safe and appropriate, rather than uploading identical bytes once per recipient. However, each resulting message must have a valid attachment relationship and independently authorized access.

Do not duplicate the underlying S3 object unnecessarily.

Ensure that:
- Recipient-specific delivery records remain correct.
- Delivery and read receipts update the right recipient.
- Failed deliveries can be retried without duplicate messages.
- List deletion does not delete already-delivered direct-chat messages.
- Access to a broadcast attachment is authorized through the actual recipient-specific message.

## 14. Storage cleanup and lifecycle

Implement cleanup for:

- Abandoned upload sessions.
- Uploaded objects never attached to a valid message.
- Deleted attachments whose retention policy permits object deletion.
- Orphaned thumbnails.
- Incomplete multipart uploads.

Do not delete an S3 object merely because one recipient deleted or hid a message if other valid messages still reference that object.

If objects are shared by multiple message attachments, use reference tracking or another safe cleanup policy.

Use idempotent cleanup operations and log only safe operational metadata.

Add an S3 lifecycle rule for aborting incomplete multipart uploads if multipart upload is used. Do not make the bucket public or introduce unnecessary storage permissions.

## 15. Security and privacy

- Keep the S3 bucket private.
- Never expose AWS credentials in the frontend.
- Use short-lived presigned URLs.
- Authorize every upload and download.
- Validate file size and type on the server.
- Use generated object keys.
- Prevent path traversal and key injection.
- Prevent unauthorized attachment ID enumeration.
- Rate-limit upload-session creation and download URL issuance.
- Prevent duplicate finalization and unauthorized deletion.
- Avoid logging signed URLs, secrets, full file contents or unnecessary personal information.
- Do not trust client-supplied sender IDs, recipient IDs or ownership claims.
- Use HTTPS for all production network traffic.
- Handle error responses without leaking bucket configuration or credentials.

### E2EE boundary

OpenE2EE integration has not yet been completed.

Do not claim that S3 server-side encryption or HTTPS makes attachments end-to-end encrypted.

For this implementation:
- Keep attachment storage metadata compatible with future client-side encryption.
- Do not invent a custom encryption scheme.
- Do not put private cryptographic keys in PostgreSQL or S3.
- Do not claim that the backend cannot read file contents while client-side E2EE is not implemented.
- Document how the current storage design can later support encrypted blobs, encrypted thumbnails and client-side key management.
