## 2. Follow the correct broadcast-list model

A broadcast list is a saved collection of recipients that the sender can reuse.

It is not a group conversation.

When a sender submits one broadcast message to a list, the system must create an independent delivery to each eligible recipient.

For example, if a list contains 100 recipients, a single send operation creates 100 recipient-specific message deliveries, each associated with that recipient's existing one-to-one chat with the sender.

### Sender experience

The sender can:

1. Create a broadcast list.
2. Name the list.
3. Select multiple registered Broadcast users.
4. Open the list as a conversation-like screen.
5. Compose and send a broadcast message.
6. See the broadcast history.
7. Inspect delivery, read and failure status for each recipient.
8. Rename the list.
9. Add or remove recipients.
10. Mute or unmute the list's notifications where appropriate.
11. Delete the list without deleting individual chat history.
12. Retry failed recipient deliveries safely.

### Recipient experience

Each recipient:

- Receives the message in their ordinary one-to-one chat with the sender.
- Does not see the broadcast list's name.
- Does not see the other recipients.
- Does not receive a group-chat message.
- Can reply privately to the sender through their normal direct chat.
- Sees normal sender identity, timestamps, message ordering and read behavior.
- Does not need to join or accept a group to receive a valid broadcast.

Replies must not be copied to the other recipients or automatically appear as messages in their broadcast list.

The sender sees replies in the ordinary direct chat with the replying recipient.

## 3. Architecture: list history versus direct messages

This distinction is mandatory.

There are two related but different views of the same send operation:

**Sender's broadcast history:** A broadcast-list message with recipient-level delivery results.

**Each recipient's direct chat:** An ordinary one-to-one message from the sender, stored and rendered using the existing direct messaging system.

Implement an explicit mapping between a broadcast message, its recipient records and the resulting direct-chat message IDs.

Do not create a shared group chat for a broadcast list.

Do not duplicate a recipient's visible message in their direct conversation.

Do not deliver the same broadcast through both the legacy message transport and a new transport.

A broadcast list is a reusable recipient definition; it is not itself a shared conversation.

## 8. Sending a broadcast message

Implement the complete message composer and delivery pipeline.

For the initial implementation, support text messages using the existing direct-chat text-message functionality. Reuse existing attachment capabilities only if they are already fully implemented and compatible with the current transport.

Do not add nonfunctional attachment buttons.

### Send operation

When the sender submits a message:

1. Validate the sender's authorization to use the list.
2. Load the current eligible membership snapshot.
3. Validate the message content and applicable limits.
4. Create a broadcast-message record.
5. Create a recipient record for each intended recipient.
6. Resolve or create the sender-recipient direct chat using the existing idempotent implementation.
7. Persist one normal direct-chat message per recipient.
8. Associate each resulting direct message with its broadcast recipient record.
9. Commit the durable work before reporting that the broadcast has been accepted.
10. Dispatch delivery events using the existing real-time delivery infrastructure or a durable outbox.
11. Update each recipient's state independently.
12. Reconcile the sender's broadcast history and delivery summary.

Use transactions and durable dispatch so a backend restart cannot silently lose accepted work.

If the recipient count is too large for one transaction or synchronous request, persist the broadcast and process its recipients in bounded batches through the existing background-processing architecture or a suitable worker. Do not introduce unnecessary microservices.

For the default 256-recipient cap, the implementation may use bounded transactional processing, but it must still handle partial failures and retries safely.

### Idempotency and duplicate prevention

A network retry must not create a second broadcast or duplicate direct messages.

Use an idempotency key scoped to the authenticated sender and the broadcast operation. Enforce the required uniqueness in PostgreSQL.

For each broadcast recipient, ensure that retrying the operation cannot create duplicate message rows.

Do not rely only on client-side disabled buttons.

### Failure handling

A broadcast can partially succeed.

For example, if 80 recipients are eligible and 76 messages are successfully persisted while 4 fail, preserve the 76 successful deliveries and record the other 4 as failed or retryable according to the actual failure.

Do not mark the entire broadcast failed if only some recipients fail.

Provide a retry operation that targets only retryable recipients.

Do not retry permanently invalid or unauthorized recipients indefinitely.

## 10. Recipient privacy and eligibility

Broadcast privacy is a core invariant.

- Recipients must not see each other.
- Recipient lists must be visible only to authorized users of the sending account.
- No recipient endpoint may expose the broadcast's complete membership.
- A recipient must not be able to retrieve the sender's broadcast-list name or list metadata through the recipient-specific message.
- Broadcast-list membership and management APIs must enforce ownership.
- Sender and recipient IDs must be derived from authenticated server state, not trusted from client payloads.
- Apply existing block and privacy policies.
- Do not deliver messages to unauthorized, blocked or ineligible recipients.
- Keep recipient-specific errors from exposing private information about other recipients.

WhatsApp's saved-sender-number rule cannot be reproduced reliably without a trustworthy application-level signal. Do not pretend that local contact membership is known to the server.

Implement eligibility using registered Broadcast accounts, the existing privacy and blocking model, and a clear app-level policy. If an explicit recipient broadcast opt-in is required by the existing product policy, enforce it server-side and provide the relevant settings. Do not silently invent a contact-sync mechanism or persist uploaded address books to infer eligibility.

## 11. Recipient-level message status

Use the existing receipt infrastructure wherever possible.

Define and document recipient states with clear transitions, such as:

- `queued`
- `processing`
- `sent`
- `delivered`
- `read`
- `failed`

Use the project's existing status vocabulary if it already provides equivalent semantics.

Do not allow a status to move backward because of duplicate or out-of-order events.

The meaning of each state must be explicit:

- `queued`: accepted into the durable broadcast pipeline but not yet handed off successfully.
- `sent`: the corresponding direct message was durably persisted and accepted by the delivery system.
- `delivered`: the recipient device acknowledged delivery according to the existing receipt protocol.
- `read`: the recipient's application acknowledged reading under the existing read policy.
- `failed`: the delivery failed and requires classification as retryable or permanent.

Store error codes and safe diagnostic metadata without leaking message contents or private information.

If the existing system has more precise states, preserve them rather than losing information through an inaccurate mapping.

### Receipt synchronization

When the recipient reads the message in the ordinary direct chat, update the associated broadcast recipient status to `read`.

When the recipient's device acknowledges delivery, update the corresponding recipient status to `delivered`.

Use the existing message-to-recipient mapping and receipt processing.

Do not independently invent delivery or read events just to update the broadcast screen.

If a recipient has disabled read receipts, follow the existing policy and do not claim a read event that the system cannot observe.
