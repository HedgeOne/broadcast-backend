You are working on **Broadcast**, a WhatsApp-inspired messaging application.

1. Incoming one-to-one messages.
2. Incoming group messages.
3. Notification registration and lifecycle management for multiple devices per user.
4. Tapping a notification to open the correct conversation.

Do not claim that push notifications are working merely because an Expo token was generated or a request was queued. Verify the complete implementation and clearly distinguish automated tests from tests that require real devices or credentials.

## 3. Notification delivery architecture

Use the Expo Push Service initially, with `expo-notifications` on the client. Expo forwards notifications to APNs on iOS and FCM on Android.

Use the existing dependency versions compatible with Expo SDK 57. Install or change dependencies only when necessary, using `pnpm` and `npx expo install` where appropriate.

Do not introduce a separate push provider unless the existing implementation requires it or you document a concrete reason.

### Message processing

When a message is sent:

1. Authenticate the sender and authorize the operation using existing rules.
2. Persist the message and required recipient/delivery state.
3. Commit the database transaction.
4. Schedule notification processing after the message transaction succeeds.
5. Identify eligible recipients and their active push-enabled devices.
6. Apply mute preferences, membership, blocking, privacy and notification eligibility checks.
7. Queue push jobs durably and process them asynchronously.
8. Record delivery-provider outcomes and retry transient failures.

Prefer the existing outbox/queue architecture if one exists. Otherwise, introduce a durable PostgreSQL-backed notification outbox or an equivalent reliable mechanism. Redis may be used as a queue accelerator, but do not make message delivery dependent on an ephemeral Redis job with no recovery mechanism.

Never send a push before the message is committed. A push failure must not cause a successfully persisted message to fail.

Ensure retries cannot create duplicate application messages or duplicate logical notification jobs. Where provider delivery is ambiguous, avoid claiming exactly-once delivery; use stable notification/job IDs and best-effort duplicate suppression.

### Recipient selection

Direct messages:
- Notify the other participant, not the sender.
- Handle the sender's other devices separately from the recipient's devices.
- Apply the recipient's chat mute setting.

Group messages:
- Notify eligible group members, excluding the sender.
- Verify current membership and any applicable group-level restrictions.
- Apply each recipient's own mute preference for that group.
- Never use one member's mute preference to suppress notifications for everyone.
- Handle group membership changes between message creation and notification processing safely.

Do not notify blocked users or violate existing privacy/security rules.

Do not notify a recipient about a message they authored just because they have another device.

### Foreground behavior

Use the existing WebSocket/message synchronization architecture while the app is active.

Avoid displaying a redundant operating-system notification when the user is actively viewing the same conversation and receiving its messages in real time. Use a reliable current-conversation/foreground state rather than assuming every foreground message should be suppressed.

When the user is on another screen, implement a sensible foreground notification behavior consistent with the app's existing UX.

The server remains authoritative for mute decisions. Client-side suppression alone is insufficient.

## 4. Device token registration and lifecycle

Implement robust client registration using `expo-notifications`.

### Client behavior

- Configure the Android notification channel before requesting permissions or registering the push token.
- Request permission contextually and respectfully. Do not repeatedly prompt after denial.
- Obtain an Expo push token using the correct EAS project ID from the app's actual configuration.
- Do not hardcode a guessed EAS project ID.
- Register the token with the authenticated backend.
- Re-register/update the token when it changes.
- Reconcile registration on app startup/login and after relevant permission changes.
- Gracefully handle denied permissions, network failures, missing configuration, offline startup and token acquisition errors.
- Unregister or deactivate the device token on logout according to the existing session/device model.
- Never deactivate a token still legitimately associated with another active session unless the existing security model requires it.
- Support multiple devices per user.
- Do not log authentication credentials or full push tokens unnecessarily.

Use the existing `devices` table if it can represent push-token registration safely. Otherwise, introduce a dedicated device-push-token table linked to users/devices.

A suitable model should capture:
- User/device association.
- Expo push token.
- Platform.
- Active/revoked status.
- Creation and last-registration timestamps.
- Last successful send and relevant error metadata where appropriate.

Add a unique constraint or equivalent protection against duplicate token registrations.

Do not use the phone number as a push-token identity. Authentication and device-token identity are separate concerns.

### Backend registration API

Design endpoints consistent with the existing API conventions. For example:

- Register/update the authenticated device's Expo push token.
- Revoke/deactivate the authenticated device's push token.
- Optionally expose the user's notification permission/registration status if the UI needs it.

Derive the user and authorized device from the authenticated session. Never accept an arbitrary user ID as proof of ownership.

Validate request schemas, token formats, platform values and rate limits.

## 5. Notification payloads and privacy

Use a minimal payload that identifies the event and destination without exposing unnecessary message content.

Suggested data fields:
- `type`: direct message or group message.
- `chatId`: authorized conversation ID.
- `messageId`: persisted message ID.
- `groupId`: only where applicable and consistent with the routing model.
- A stable notification/job identifier where useful.

Do not trust identifiers received from a push notification without validating them through normal authenticated APIs.

**Default to privacy-preserving notifications.** Do not put message text, attachment URLs, phone numbers, authentication tokens or other sensitive content in push payloads.

Use a generic notification title/body initially, such as:
- Direct chat: "New message"
- Group: "New group message"

If the existing product already has a notification-preview preference, honor it. Otherwise, keep previews generic and do not invent a nonfunctional settings toggle. A richer preview setting can be added separately if needed.

This privacy requirement is especially important because end-to-end encryption is not currently established as functional in this project. Do not claim E2EE. TLS, S3 encryption at rest and private push payloads are not equivalent to E2EE.

## 6. Sending notifications through Expo

Implement a backend notification provider/service that sends queued jobs to the Expo Push API.

Requirements:
- Batch requests according to Expo's documented limits.
- Process push tickets and subsequent push receipts.
- Handle invalid or unregistered tokens by deactivating the affected token.
- Retry transient network errors, rate limits and temporary provider failures with bounded exponential backoff and jitter.
- Do not retry permanent payload or token errors indefinitely.
- Respect provider limits and prevent an outage from creating an unbounded queue.
- Track queued, processing, accepted, delivered-to-provider/device where actually known, failed and retryable states accurately.
- Distinguish Expo accepting a request from the notification actually appearing on a device. Do not treat an Expo push ticket as proof that the user saw the notification.
- Include operational logging and metrics without recording message contents or sensitive credentials.

Use a configurable provider endpoint and sensible timeouts. Never send push notifications directly from the mobile app using privileged credentials.

All Expo access tokens or other server-side secrets must remain on the backend. Do not add secrets to Expo public configuration or commit them to Git.

Document required environment variables and deployment configuration without exposing their values.

## 9. Mute data model and expiry semantics

Create a per-user, per-conversation notification preference model using the existing schema if appropriate. Otherwise, add a migration.

The model must support:
- User ID.
- Conversation ID or a correctly normalized chat/group reference.
- Muted status.
- Mute expiry timestamp, nullable for Always.
- Created/updated timestamps.

Prefer a normalized model that prevents conflicting chat and group records. Follow the actual domain model; do not blindly introduce a generic table if the existing schema already has a suitable design.

Use database constraints to enforce uniqueness per user/conversation.

Semantics:
- Unmuted: no active mute.
- Timed mute: mute remains active while the authoritative server time is before the expiry.
- Always: active mute with no expiry.
- Expired timed mute: notifications resume automatically without requiring the user to open the app.
- Unmute: immediately removes the active mute.

Use UTC timestamps and server-side time for expiry decisions. Never depend on the device clock.

A background cleanup job may normalize expired records, but correctness must not depend on that job running. Notification eligibility must check whether the mute is active at send time.

Do not store a duration alone and attempt to recalculate the expiry on every request.
