# Implement End-to-End Encryption (E2EE) in Broadcast Using OpenE2EE

You are the senior mobile security and backend engineer responsible for implementing genuine end-to-end encryption in **Broadcast**, an existing WhatsApp-inspired messaging application.

This is a security-critical architectural change. Do not begin by blindly installing packages or replacing the messaging system. First audit the existing application and the exact OpenE2EE SDK release, establish a verified integration plan, then implement and test the system end-to-end.

The goal is to ensure that message content and attachment plaintext are accessible only to authorized endpoints, not to the Broadcast backend, OpenE2EE hosted relay, PostgreSQL, Redis, S3 or push-notification provider.

Passing TypeScript checks or seeing an encrypted-looking database field is not proof of E2EE.

# PART 1 — FIXED ARCHITECTURAL DECISIONS

Treat these as the requirements for this project.

## 1. Mobile runtime

- Frontend: Expo React Native and TypeScript.
- Use Expo development builds for E2EE functionality.
- Continue supporting Expo Go for unrelated development where feasible.
- Do not claim the OpenE2EE SQLCipher store works in Expo Go.
- Preserve the existing Expo Router, design system, navigation, authentication and application architecture.
- Use SDK-compatible dependencies for the project's actual Expo SDK and React Native versions.
- The current frontend has Expo SDK 57, React Native 0.86 and Expo Router. Verify the actual installed versions before modifying dependencies.
- The app must build and run on both iOS and Android.
- Do not switch to bare React Native or rewrite the application merely to introduce encryption.

## 2. E2EE SDK

Use OpenE2EE's Signal Protocol SDK, subject to the mandatory version and licensing audit in Part 2.

The current official Expo documentation references:

`@open-e2ee/signal-protocol-sdk@11.0.0`

This is a candidate version, not permission to install it without verification. Inspect the current npm package, published version, official documentation, release tag, package metadata and license before pinning a version.

Use the SDK's documented APIs and supported adapters. Do not invent imports, methods, callback names, configuration fields or protocol behavior.

OpenE2EE implements its own versioned Signal Protocol profile. It is not wire-compatible with the Signal Messenger app or libsignal. Do not claim interoperability with Signal.

## 3. Relay

Use the **OpenE2EE hosted Signal Protocol Relay for production**, after the integration has been validated against the development/sandbox environment.

Requirements:
- Use separate development and production relay environments and credentials.
- Never put relay administrative secrets, private credentials or server-only tokens in the mobile application.
- Use the SDK's documented hosted-client integration.
- Integrate the existing Broadcast authentication system with relay identity assertions.
- Use short-lived, authenticated assertions generated by the trusted backend or another documented secure mechanism.
- Never allow the client to mint an assertion for an arbitrary user or device.
- Verify ownership, device registration, assertion audience, expiry, signature and replay protections according to the relay's documented contract.
- Do not accept user IDs supplied by the client as proof of identity.
- Do not activate a paid relay plan, accept legal terms, commit to a contract or deploy to production without explicit human authorization.

Do not implement a custom relay unless the official hosted-relay interface cannot satisfy a documented requirement. If that happens, stop and explain the blocker instead of silently changing the architecture.

## 4. Recovery policy

For the initial release, **there is no message-history backup or server-side key recovery**.

- Private identity keys, prekeys, session state and ratchet state remain in the SDK's protected device-local storage.
- The SDK's SQLCipher database and its secure-storage vault key must use the documented storage architecture.
- Do not upload private keys, session state, ratchet keys, database encryption keys or the vault key to Broadcast servers or the hosted relay.
- Do not implement an undisclosed key escrow.
- Explain to users that losing the device, deleting app data or reinstalling may permanently destroy access to historical encrypted messages.
- A new installation may generate a new cryptographic identity.
- Handle the resulting identity change safely and visibly.
- Do not promise recovery of old messages through phone OTP alone.

Use the documented Expo storage adapter and secure vault. Keep the SDK-owned encrypted database separate from the application's existing SQLite cache database.

## 5. Encryption scope

The final target includes:

1. One-to-one text messages.
2. Group messages.
3. Broadcast-list messages.
4. Photos and images.
5. Videos.
6. Audio and voice messages.
7. Documents and other supported attachments.
8. Message replies, reactions, edits, deletions and other content-bearing message operations already implemented by the app.
9. Push notifications that reveal no plaintext message content.
10. Shared media, links, docs and starred-message experiences that operate on client-decrypted content.

Do not claim all these features are encrypted until each has passed its applicable tests.

If the SDK does not support an operation or the current architecture needs an additional security protocol, document the gap and implement only a properly reviewed solution. Do not substitute custom cryptography for a missing SDK capability.

## 6. Historical test data

Before the first end-to-end encryption rollout, clear existing **test/staging message data** so old plaintext messages cannot be mistaken for encrypted messages.

This is a mandatory migration requirement, but it is not permission to destroy arbitrary data.

- Identify the exact database, environment, accounts and records that constitute test data.
- Confirm that the target is a disposable test/staging environment.
- Use an explicit environment check and a deliberate, documented migration/reset procedure.
- Back up any data required for debugging or migration validation before resetting it.
- Never truncate production tables or delete real users' messages automatically.
- Do not perform destructive actions if the environment cannot be positively identified.
- Report exactly what was cleared, from which environment, and by which command or migration.

Do not attempt to convert historical Base64-encoded plaintext into ciphertext and call it E2EE.

# PART 4 — RELAY INTEGRATION AND MESSAGE TRANSPORT

## 1. Establish the new transport boundary

Use the OpenE2EE hosted client and relay for encrypted message delivery, following the verified version's documented interfaces.

The intended message flow is:

1. The sender writes plaintext locally.
2. The sender's device encrypts using the SDK.
3. The relay receives the encrypted envelope and permitted routing metadata.
4. The recipient's device retrieves the envelope.
5. The recipient's SDK decrypts and authenticates it locally.
6. The UI renders the decrypted message from authorized local application state.

The Broadcast backend must not receive plaintext content as part of this flow.

Do not keep the old plaintext-send path active as a fallback when E2EE is enabled.

## 2. Integrate with existing Fastify services

Preserve existing backend responsibilities where they remain appropriate:
- Account authentication.
- Application authorization.
- Chat and group membership.
- Broadcast-list membership and recipient management.
- Device-to-account mapping.
- Notification registration.
- Permitted message delivery metadata.
- Abuse prevention and rate limiting.
- Existing operational monitoring.

Adapt the current REST and WebSocket architecture to the hosted relay rather than maintaining two competing message-delivery systems.

Do not send a plaintext copy to the current Fastify message endpoint while also sending ciphertext through the relay.

Do not persist decrypted message bodies in PostgreSQL, Redis or server-side caches.

The backend may retain only the metadata needed for application behavior and security, such as permitted sender/device identifiers, conversation IDs, opaque message references, delivery state and timestamps.

Use the SDK's documented envelope and identifier semantics. Never invent a wire format or assume the SDK accepts arbitrary payloads.

## 3. Message types and serialization

Support existing message types, as applicable:
- Text.
- Reply/reference.
- Reaction.
- Edit/delete operation.
- Attachment pointer.
- Group message.
- Broadcast recipient message.
- Other existing content-bearing message types discovered during the audit.

The complete content-bearing payload must be encrypted before transport.

Only routing information strictly required by the protocol and service may remain visible to the relay. Minimize metadata leakage where possible.

Validate decrypted application payloads locally before rendering them. Treat decrypted content as untrusted input: a valid encrypted message can still contain malformed or unsupported application data.

Handle unknown schema versions safely. Never render ciphertext as if it were readable text.

## 4. Idempotency, offline delivery and synchronization

# PART 15 — ENGINEERING RULES

- Inspect before changing.
- Pin the verified SDK version.
- Follow the exact version's documentation.
- Do not mix API examples across SDK releases.
- Do not invent cryptographic APIs.
- Do not implement custom cryptography.
- Do not send plaintext to the backend as a fallback.
- Do not store private keys on the server.
- Do not assume phone OTP is proof of cryptographic identity.
- Do not expose AWS credentials or relay administration secrets.
- Do not silently downgrade an E2EE conversation.
- Do not truncate production data.
- Do not claim a message is encrypted until the actual SDK encrypt/decrypt path is verified.
- Do not claim media is E2EE until the recipient decrypts ciphertext locally and server-side storage is verified.
- Do not claim group E2EE until membership changes and key rotation are tested.
- Do not claim a conversation is verified until identity verification has succeeded.
- Do not report tests as passed unless they were actually run.
- Do not claim a security audit has been completed unless an independent audit has actually occurred.
