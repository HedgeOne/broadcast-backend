# 2. AUTHENTICATION PROVIDER DECISION

## Current authentication method

For the initial version, users authenticate using:

**Email + verification code**

The verification code is sent using:

**MSG91**

This is the current production provider.

Do NOT implement mobile-number OTP yet.

---

# 3. FUTURE AUTHENTICATION

Later we will switch from:

```text
Email
  ↓
MSG91
  ↓
Verification code
```

to:

```text
Mobile number
  ↓
MSG91 / SMS provider
  ↓
OTP
```

Therefore, DO NOT tightly couple the authentication domain to email.

The architecture must allow:

```text
Authentication
      │
      ▼
Verification Provider Interface
      │
      ├── Email / MSG91
      │
      └── Mobile OTP / future provider
```

The rest of the application should not care which verification provider is being used.

# 5. AUTHENTICATION FLOW

Implement the following initial flow.

## Step 1 — Enter email

User opens the application.

They see:

```text
Welcome to Broadcast

Enter your email to continue

[ Email address ]

[ Continue ]
```

User enters:

```text
sarthak@example.com
```

---

## Step 2 — Request verification code

Mobile calls:

```http
POST /auth/request-code
```

Payload:

```json
{
  "email": "sarthak@example.com"
}
```

Backend:

```text
validate email
      ↓
normalize email
      ↓
rate limit
      ↓
generate verification code
      ↓
hash code
      ↓
store verification challenge
      ↓
send through MSG91
      ↓
return success
```

Do NOT return the actual verification code to the client.

---

# 6. VERIFICATION CODE SECURITY

Never store the plaintext verification code.

Store a hash.

For example:

```text
user enters:
123456

server stores:
hash(123456)
```

When the user submits the code:

```text
123456
    ↓
hash
    ↓
compare
```

The verification challenge must have:

- expiration
- attempt limit
- resend cooldown
- rate limiting
- consumed state

Do not allow unlimited verification attempts.

---

# 7. VERIFY CODE

Mobile calls:

```http
POST /auth/verify-code
```

Payload:

```json
{
  "email": "sarthak@example.com",
  "code": "123456"
}
```

Backend:

```text
validate
   ↓
find active challenge
   ↓
check expiration
   ↓
check attempt limit
   ↓
verify hash
   ↓
consume challenge
   ↓
find/create user
   ↓
create device
   ↓
create session
   ↓
issue tokens
```

# 12. MSG91 INTEGRATION

Create a dedicated MSG91 provider.

Do NOT call MSG91 directly from route handlers.

Use something conceptually like:

```text
src/modules/auth/
├── auth.routes.ts
├── auth.service.ts
├── auth.repository.ts
├── verification/
│   ├── verification-provider.ts
│   └── msg91-provider.ts
└── schemas.ts
```

The interface should conceptually resemble:

```ts
interface VerificationProvider {
  sendVerificationCode(input: {
    destination: string;
    code: string;
    channel: "email" | "sms";
  }): Promise<void>;
}
```

The exact interface can be improved based on the existing codebase.

The important requirement is that:

**AuthService must not depend directly on MSG91.**

# 16. JWT / SESSION ARCHITECTURE

Authentication should result in:

```text
access token
+
refresh token
```

The database already contains:

```text
sessions
```

and:

```text
devices
```

Use those entities.

The model should be:

```text
User
 │
 ├── Device A
 │     └── Session
 │
 ├── Device B
 │     └── Session
 │
 └── Device C
       └── Session
```

Do NOT assume one user has one session.

---

# 17. ACCESS TOKENS

Access tokens should be short-lived.

They should contain the minimum required claims.

Do not put unnecessary personal information into JWTs.

At minimum, the backend should be able to resolve:

```text
user_id
device_id
session identity
```

Use the existing Fastify JWT infrastructure.

---

# 18. REFRESH TOKENS

Refresh tokens should:

- be long-lived relative to access tokens
- be stored hashed in PostgreSQL
- be associated with a device/session
- be revocable
- support rotation
- expire
- not be stored plaintext in PostgreSQL

Do not store raw refresh tokens in the database.
