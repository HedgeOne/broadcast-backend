# 1. What We Are Building

We are building a production-grade mobile messaging application inspired by WhatsApp.

The application is a modern, realtime, offline-first messaging platform.

The goal is NOT to build a toy WhatsApp clone. The architecture should be designed from the beginning to support:

- Large numbers of users
- Multiple devices per user
- Offline usage
- Reliable message delivery
- Realtime messaging
- End-to-end encryption
- Groups
- Broadcast Lists
- Media
- Push notifications
- Message synchronization
- Message ordering
- Idempotent retries
- Future horizontal scaling
- AWS production deployment

We are deliberately excluding some WhatsApp features.

### Broadcast Lists

Broadcast Lists are a first-class messaging primitive.

A Broadcast List is NOT a group.

For example:

Alice creates:

```text
"Customers"

Recipients:
- Bob
- Charlie
- David
```

Alice sends one broadcast message.

Bob, Charlie and David should each receive the message in their normal 1-to-1 conversation with Alice.

They must NOT see each other as recipients.

The sender sees the Broadcast List as an organizational object.

The backend stores the logical broadcast message once and stores recipient-specific delivery/read state separately.

# 11. Message Reliability

Message delivery must be designed for unreliable networks.

Every outbound message has a client-generated ID:

```text
client_message_id
```

The server generates its own:

```text
message.id
```

If the mobile client sends the same message again because of a timeout/reconnect, the backend must recognize the same client ID and avoid creating a duplicate.

This is critical.

Example:

```text
Client:

client_message_id = abc-123

        │
        ▼

POST /messages

        │
        ▼

Server creates message
id = server-generated UUID

        │
        X
Connection lost

        │
        ▼

Client retries abc-123

        │
        ▼

Server recognizes abc-123
and returns the existing message
```

No duplicate message should be created.

---

# 12. Message Ordering

Do NOT use timestamps as the authoritative ordering mechanism.

Every chat has a monotonically increasing:

```text
sequence
```

Example:

```text
chat_id = X

sequence 1001
sequence 1002
sequence 1003
sequence 1004
```

This allows reliable synchronization.

Example:

```text
Client currently has sequence 1001.

Server has:

1001
1002
1003
1004
1005
...
1057
```

The client can request:

```text
1002 → 1057
```

This is much more reliable than asking for messages based purely on timestamps.

---

# 13. Read and Delivery Receipts

Do not create one database row for every normal message receipt.

For normal chats, use:

```text
chat_members.last_delivered_sequence
chat_members.last_read_sequence
```

For example:

```text
last_delivered_sequence = 1057
last_read_sequence = 1054
```

This means the member has received through 1057 and read through 1054.

This dramatically reduces database write volume.

Broadcast Lists are different.

Broadcast messages require recipient-specific state:

```text
broadcast_message_recipients
```

because Bob may have read the message while Charlie has not.

# 14. End-to-End Encryption

The architecture must eventually support Signal Protocol-style E2EE.

Do NOT implement cryptographic primitives manually.

The system should use a mature, audited cryptographic implementation/library.

Conceptually:

```text
User
  │
  ├── Device A
  │     ├── Identity Key
  │     ├── Signed Pre-Key
  │     └── One-Time Pre-Keys
  │
  └── Device B
        ├── Identity Key
        ├── Signed Pre-Key
        └── One-Time Pre-Keys
```

The server should primarily see ciphertext.

The database therefore contains fields such as:

```text
ciphertext
encrypted_metadata
identity_key_public
signed_prekey_public
one_time_prekeys
```

The actual E2EE implementation is NOT being built yet.

Do not invent a custom cryptographic protocol.

---

# 15. Multi-Device Architecture

Multi-device support is a first-class requirement.

A user is not equivalent to a device.

Conceptually:

```text
User
 ├── Device A
 ├── Device B
 └── Device C
```

Each device can have:

- Its own session
- Its own cryptographic identity
- Its own push token
- Its own WebSocket connection

The backend must therefore never assume:

```text
one user = one device
```

# 20. Important Database Decisions

These decisions are already made.

## PostgreSQL is authoritative

Do not duplicate authoritative business state into Redis.

## UUID primary keys

Tables use UUID primary keys.

Application-level UUIDv7 generation can be introduced later for time-sortable identifiers.

The PostgreSQL schema currently uses:

```sql
gen_random_uuid()
```

for safe database-side UUID generation.

## Message sequence

Messages use:

```text
chat_id + sequence
```

for deterministic ordering.

## Client idempotency

Messages use:

```text
client_message_id
```

to prevent duplicate messages during retries.

## Broadcasts

Broadcast Lists are separate from groups.

## Read state

Normal chats use:

```text
last_delivered_sequence
last_read_sequence
```

Broadcasts use recipient-specific state.

## E2EE

Message bodies are modeled as opaque ciphertext.

## Multi-device

Devices are separate entities from users.

# 27. Offline-First Design

The mobile application should behave as:

```text
UI
 ↓
Local SQLite
 ↓
Sync Engine
 ↓
REST/WebSocket
 ↓
Backend
```

Not:

```text
UI
 ↓
Network
 ↓
Backend
```

The local database should be able to provide the UI with existing data immediately.

Outbound messages should enter a local pending queue.

Example:

```text
User sends message
       │
       ▼
SQLite pending message
       │
       ▼
Optimistic UI
       │
       ▼
Network available?
   ┌───┴────┐
   │        │
  yes       no
   │        │
   ▼        ▼
server    wait
   │
   ▼
acknowledgement
   │
   ▼
mark sent
```

# 28. Reconnection

The client should eventually implement an explicit connection state machine:

```text
DISCONNECTED
      ↓
RECONNECTING
      ↓
AUTHENTICATING
      ↓
SYNCING
      ↓
CONNECTED
```

After reconnecting, the client must synchronize from its last known server sequence rather than assuming it received every WebSocket event.

WebSocket events are realtime acceleration, not guaranteed durable delivery.

# 29. Coding Principles

When implementation begins:

### TypeScript

Use strict TypeScript.

Avoid:

```ts
any
```

unless there is a genuinely justified boundary.

### Validation

Use Zod at API boundaries.

### Database

Use transactions for operations that modify multiple related records.

### Idempotency

Every retryable write should have an idempotency strategy.

### Authorization

Never rely on the frontend for authorization.

Every backend operation must verify:

- authenticated user
- ownership
- membership
- permissions
- resource access

### Security

Never trust client-provided:

- user IDs
- chat membership
- group roles
- message ownership
- broadcast ownership
- authorization state

### Errors

Use structured application errors.

Do not leak:

- database internals
- stack traces
- secrets
- cryptographic material

to clients.

### Logging

Use structured logs.

Never log:

- plaintext message contents
- private keys
- authentication tokens
- refresh tokens
- message ciphertext unnecessarily
- personal data unnecessarily

# 32. Engineering Direction

Build this as a serious production system.

Do not:

- Build everything in one giant file
- Put business logic directly inside Fastify route handlers
- Use Redis as the source of truth
- Store large files in PostgreSQL
- Send large media through the API server
- Depend on WebSocket delivery for durability
- Use timestamps as the message ordering mechanism
- Create duplicate message records during retries
- Assume one user has one device
- Treat broadcast lists as groups
- Implement custom cryptography
- Create microservices prematurely
- Add unnecessary infrastructure before it is needed

Prefer:

```text
thin route
    ↓
validated request
    ↓
service
    ↓
repository / database
    ↓
domain event
    ↓
realtime / worker
```

Keep modules isolated and testable.
